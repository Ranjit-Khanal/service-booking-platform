# Idempotency

There are two idempotency mechanisms in the code, protecting two different operations:

| # | Operation | Duplicate source | Mechanism | State stored in |
|---|---|---|---|---|
| 1 | `POST /api/bookings` | Client/network retries, double submits | `Idempotency-Key` header + Redis `SET NX` + payload hash | Redis `slotbook:idem:{key}` (TTL 24h), backed by `bookings.idempotency_key` unique index |
| 2 | `booking.created` consumer | RabbitMQ at-least-once redelivery, consumer self-retries | Insert-first dedupe table | Postgres `processed_events` (no TTL) |

Operations that are idempotent **by design**, without a key:

- `POST /api/bookings/{id}/cancel`: the target state is absolute. A repeat returns
  `200` with `changed: false` and the same booking; the row lock serialises concurrent
  repeats (see [concurrency.md](concurrency.md#cancellation)).
- `POST /api/admin/failures` sets absolute values; `POST /api/admin/cache/flush` is
  harmless to repeat.

Not idempotency-protected: the payment charge itself at the provider level (see
[below](#payment-provider-idempotency)).

## 1. Booking creation

### Problem

A client sends `POST /api/bookings`. The server claims the slot, charges the card,
confirms, and the response is lost (client timeout, dropped Wi-Fi, HAProxy `timeout
server` of 50s). The client does not know whether it was booked. If it simply retries:

### Naive implementation

```text
attempt 1 ─► claim slot ─► charge ✔ ─► confirm ─► 201 ✗ (lost)
attempt 2 ─► claim slot ✗ 409 SLOT_UNAVAILABLE
```

For a single slot the row lock already prevents a *second booking*, but the customer
now sees an error for a booking that actually succeeded. With a naive design where the
slot check was weaker, or for any operation without a natural unique constraint, the
retry would charge twice.

### Actual implementation

`CreateBookingUseCase.execute` + `createRedisStack().idempotency`:

```text
hash = sha256({serviceId, slotId, email.lower, name.trim})

begin(key):
  SET slotbook:idem:{key} '{"status":"in_progress","requestHash":…}' EX 86400 NX
    OK   → 'acquired'      → do the work
    nil  → GET the record
           status == 'in_progress' → 'in_progress' → 409
           otherwise              → 'completed'   → replay

… work …

complete(key):
  SET slotbook:idem:{key} '{"requestHash":…,"statusCode":201,"body":{bookingId,status}}' EX 86400
```

Replay path (`begin === 'completed'`):

1. `GET` the record. If its `requestHash` differs from this request's hash →
   `409 CONFLICT` with `details.code = 'IDEMPOTENCY_CONFLICT'`.
2. Load the booking from Postgres by `idempotency_key`, return `200` with
   `replayed: true`.

Notes on the design:

- **`SET NX` is the atomic "claim"**. Of N concurrent requests with the same key,
  exactly one gets `OK`, on any replica, because the check-and-set is a single Redis
  command.
- **The replay returns current state from Postgres**, not the stored response body. The
  stored body is only used to carry the hash. A replay after a later state change would
  reflect that change.
- **Postgres is the backstop.** `bookings.idempotency_key` is `UNIQUE`, so even if the
  Redis record disappears, a second booking row with the same key cannot be inserted.
- The key is **global**, not scoped to a customer or endpoint. Two clients choosing the
  same key collide. Keys generated by the demo client are `crypto.randomUUID()`.

### Duplicate handling, case by case

| Case | Result |
|---|---|
| Same key, sequential, first succeeded | `200`, `replayed: true`, same booking. No second claim or charge. |
| Same key, concurrent (double click, two tabs) | One proceeds; the other gets `409 CONFLICT` "already in progress" immediately. It is not queued or awaited — the client must retry later. |
| Same key, different body, first **completed** | `409` with `IDEMPOTENCY_CONFLICT`. |
| Same key, different body, first **still in progress** | `409` "in progress". The hash is not compared on this branch. |
| Same key after the first attempt **failed** (402 declined, 500 timeout, circuit open, 503) | **`409` "in progress" for 24 hours.** Failures never call `complete()` and never delete the record, so the key is stuck in `in_progress` until TTL. The client must use a new key. |
| Same key after TTL (24h) expired | Treated as new. Claim fails with `409 SLOT_UNAVAILABLE` if the original booking holds the slot; if the original failed and the slot was released, the new claim succeeds and `INSERT booking` hits `bookings_idempotency_uq` → 500, leaving the slot `booked` with no booking. |
| Redis unavailable | `begin` throws → request fails (fail-closed). No work is done without an idempotency record. |

The demo client generates a **new** key on every submit (`ServiceDetailPage.tsx`), so a user
retrying through the UI after a failure is not blocked by the stuck record. It also means
the UI does not get replay protection for a user double-submitting after a lost
response — only automated retries that reuse the key do.

### What happens if the process crashes halfway

| Crash point | Redis record | Postgres | Customer | Recovery |
|---|---|---|---|---|
| After `begin`, before claim | `in_progress` 24h | unchanged | nothing | Retry with same key → 409 for 24h. New key works. |
| After claim, before `INSERT booking` | `in_progress` | slot `booked`, no booking | nothing | **None.** Slot is lost inventory. |
| After insert, during/after charge, before confirm | `in_progress` | booking `pending_payment`, slot `booked` | **possibly charged** | **None.** Needs manual reconciliation against the provider. |
| After confirm, before publish | `in_progress` | booking `confirmed` | charged | No notification is ever sent. Same key → 409. Customer can find the booking via `GET /api/bookings?email=`. |
| After publish, before `complete` | `in_progress` | `confirmed` | charged, notified | Same key → 409 for 24h instead of a replay. |
| After `complete` | `completed` | `confirmed` | charged, notified | Replay works. |

The same table applies to a request that **errors** rather than crashes at the
publish step: with `failBrokerPublish` on, the booking is `confirmed` and charged, the
client receives `503`, and the key is stuck — the client is told to retry, and every
retry with the same key returns 409.

### Payment provider idempotency

The use case passes `idempotencyKey` into `PaymentProvider.charge()`, and a real
provider (Stripe, for example) would use it to deduplicate charges across the in-process
retry loop and across crashes. None of the adapters in the repository forward it:
`MockPaymentProvider` generates a fresh `mock_{uuid}` reference on every call, and the
Stripe/eSewa adapters are stubs. So inside a single request, a timed-out attempt that
actually succeeded at the "provider" and a retried attempt would be two charges.
With the mock this is invisible; with a real provider, forwarding the key is required.

### Trade-offs

- **Redis as the primary record.** Fast and shared, but not durable (no AOF/RDB config in
  Compose) and subject to eviction under memory pressure. The Postgres unique index
  catches the worst outcome (duplicate booking) but not the user-visible one (a retry
  returns 409/500 instead of the original result).
- **Fail-closed on Redis loss.** No bookings while Redis is down. Chosen deliberately
  over the risk of double charges.
- **No release on failure.** Simple, but it turns every transient failure into a
  24-hour lockout for that key. Deleting the record (or storing the failure response for
  replay) on non-retryable failures would fix it.
- **Two-phase record without fencing.** If a request somehow ran longer than the TTL, a
  second request could acquire the key while the first was still working. With a 24h TTL
  this is theoretical.

## 2. Notification consumer

### Problem

RabbitMQ delivers **at least once**. A message is redelivered if the worker dies before
`ack`, if the channel closes, or when the consumer's own retry logic republishes it.
Sending the confirmation email twice is the visible symptom.

### Actual implementation

`LoggingNotificationSender.sendBookingConfirmation`:

```sql
INSERT INTO processed_events (event_id, correlation_id)
VALUES ('booking.created:{bookingId}:email', $2)
ON CONFLICT (event_id) DO NOTHING
RETURNING event_id;
-- 0 rows → duplicate → return without sending
```

The dedupe key is derived from the **business identity** (booking ID + side-effect name),
not from the AMQP `messageId` or delivery tag, so a republished retry copy and a
broker redelivery both collapse onto the same row.

### Failure scenarios

| Scenario | Result |
|---|---|
| Message delivered twice | Second insert conflicts → logged as "Duplicate notification suppressed" → acked. |
| Worker crashes after insert, before "send" | On redelivery the row exists → **email never sent**. The pattern is *mark-then-send* (at-most-once for the side effect). With the current logging stub nothing is lost; with a real email provider this would silently drop emails. |
| Worker crashes after send, before ack | Redelivered, suppressed. Correct. |
| Postgres down | Insert throws → consumer retry path (3 republishes) → DLQ. |
| `processed_events` growth | Unbounded; no cleanup job. |

### Trade-offs

- Insert-first gives exactly-once *bookkeeping* but at-most-once *delivery* of the side
  effect. The usual alternatives are send-then-mark (at-least-once email, occasional
  duplicate) or storing a pending/sent status and using the email provider's own
  idempotency key. Which is right depends on whether a duplicate or a missing email is
  worse for the product.
- Dedupe lives in the same Postgres as bookings, so the worker gains a dependency on it.
